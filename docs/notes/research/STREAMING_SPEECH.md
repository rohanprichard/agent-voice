# Streaming speech recognition and synthesis on Apple Silicon

Research date: September 24, 2026.

This note examines whether TalkToMe can move from whole-buffer recognition and synthesis to a stream-in, chunks-out design on an Apple Silicon Mac. It covers what is genuinely streamable, what it costs, and what is a bad idea. The user's stated architecture — "stream input audio in, stream output chunks out" — turns out to be two separate questions with two different answers, because the recognition half and the synthesis half are constrained by different things.

Two kinds of number appear below. Quoted numbers come from the source named beside them, and are labelled as a vendor claim or a measurement. Numbers labelled "measured here" were produced for this note on the development machine, an Apple M1 Pro with 16 GB of memory running macOS 27.0, using the application's own installed model files and its own transcription settings (`device="cpu"`, `compute_type="int8"`, `cpu_threads=4`, `beam_size=3`, `vad_filter=True`, `condition_on_previous_text=False`, as set in `src/talktome/speech.py`). The scripts are not committed; each measurement is described so that it can be repeated. Where the source says nothing, this note says so rather than estimating.

## 1. Whisper is not a streaming model

The first question has a definite answer from the primary source. Whisper is an encoder–decoder trained on fixed thirty-second windows, and nothing in the released model accepts audio incrementally. The paper states it directly:

> Whisper models are trained on 30-second audio chunks and cannot consume longer audio inputs at once. This is not a problem with most academic datasets comprised of short utterances but presents challenges in real-world applications which often require transcribing minutes- or hours-long audio. We developed a strategy to perform buffered transcription of long audio by consecutively transcribing 30-second segments of audio and shifting the window according to the timestamps predicted by the model. [Whisper paper, section 3.8](https://ar5iv.labs.arxiv.org/html/2212.04356)

The OpenAI repository says the same in its Python-usage section: "Internally, the `transcribe()` method reads the entire file and processes the audio with a sliding 30-second window, performing autoregressive sequence-to-sequence predictions on each window." ([openai/whisper README](https://raw.githubusercontent.com/openai/whisper/main/README.md)). The words "streaming", "real-time" and "low-latency" do not occur in the Whisper paper at all. A search of the full paper text returns zero matches for each of "streaming", "real-time", "real time", "low-latency", "low latency", "simultaneous" and "online decoding". Whisper is a batch model, and the paper never claims otherwise.

`faster-whisper` inherits the constraint exactly. It reimplements the same model in CTranslate2 and is "up to 4 times faster than openai/whisper for the same accuracy" ([faster-whisper README](https://raw.githubusercontent.com/SYSTRAN/faster-whisper/master/README.md)), but it is faster at the same job, not a different job. Its API is worth reading carefully, because it is the source of a common confusion: `transcribe()` returns a tuple of `(segments, info)` where `segments` is a generator, and the README warns that "`segments` is a *generator* so the transcription only starts when you iterate over it". That laziness is over the *output* — decoding window after window of an audio buffer that has already been supplied in full. It is not a stream input. There is no method on `WhisperModel` that accepts more audio later; the whole buffer is an argument. TalkToMe already passes a complete buffer and joins the segments, at `src/talktome/speech.py` in the `transcribe` method.

That is why every project calling itself "streaming Whisper" is a *policy* wrapped around a batch model rather than a streaming model. The canonical policies are LocalAgreement-n and AlignAtt, both described from the source in the next subsection. The shape is always the same: keep a buffer of unconfirmed audio, run the whole batch model over it again on a timer, and decide which part of the new transcript is stable enough to publish.

### The canonical implementations

`ufal/whisper_streaming` is the reference implementation of the sliding-window approach and the origin of most of the others. Its README states the policy: "LocalAgreement-n policy: if n consecutive updates, each with a newly available audio stream chunk, agree on a prefix transcript, it is confirmed", with n = 2 in practice. It is MIT licensed and was last committed on 12 November 2025, but the README now opens with a warning about its own status: "In 2025, WhisperStreaming is becaming outdated, replaced by [SimulStreaming]". Its stated latency is the demonstration paper's abstract figure of "3.3 seconds latency on unsegmented long-form speech transcription test set", which is measured on an NVIDIA A40 GPU with the `large-v2` model ([README](https://raw.githubusercontent.com/ufal/whisper_streaming/main/README.md), [paper](https://aclanthology.org/2023.ijcnlp-demo.3/)). The parameter that controls the trade-off is `--min-chunk-size`, documented as "Minimum audio chunk size in seconds. It waits up to this time to do processing", with a default of 1.0 second; the buffer is trimmed at `--buffer_trimming_sec`, default 15 seconds ([`whisper_online.py`](https://raw.githubusercontent.com/ufal/whisper_streaming/main/whisper_online.py)). Both defaults matter in section 2.

`ufal/SimulStreaming` is the author's replacement and the state of the art in this family. It merges whisper_streaming with Simul-Whisper and uses the AlignAtt policy, which "uses encoder-decoder attention to determine, which part of source is being decoded at each step of decoding loop. If attention reaches a 'dangerous zone' near the end of current autio buffer, decoding stops." Its licence is MIT, and it was last committed on 19 June 2026 ([GitHub API](https://api.github.com/repos/ufal/SimulStreaming/commits?per_page=1)). It claims to be "~5-times faster than our previous release called WhisperStreaming, thanks to efficient simultaneous policy" — a vendor claim in a README, not a benchmark. More important for this project is its hardware statement: "Recommended HW is GPU with at least 10G VRAM, to run the best-performing Whisper model large-v3 with 1.5B parameters. The code works also on CPU but would be too slow for real-time." That sentence is the single most useful primary-source judgement on running sliding-window Whisper without a GPU ([README](https://raw.githubusercontent.com/ufal/SimulStreaming/main/README.md)).

`whisper.cpp`'s `stream` example is the implementation people most often mistake for a streaming engine. Its own README is candid: "This is a naive example of performing real-time inference on audio from your microphone. The `whisper-stream` tool samples the audio every half a second and runs the transcription continuously." It offers a second mode, enabled by `--step 0`, described under the heading "Sliding window mode with VAD": "the tool will transcribe only after some speech activity is detected... When silence is detected, it will transcribe the last `--length` milliseconds of audio and output a transcription block that is suitable for parsing." The README gives the two invocations, `--step 500 --length 5000` for the rolling mode and `--step 0 --length 30000` for the VAD mode, and states **no latency figure** for either. It is MIT licensed and by far the most maintained project in this list — last commit 24 September 2026 — but for our purposes it is the same re-decode loop with a Metal backend rather than a streaming decoder ([stream README](https://raw.githubusercontent.com/ggml-org/whisper.cpp/master/examples/stream/README.md), [repo metadata](https://api.github.com/repos/ggml-org/whisper.cpp)).

`collabora/WhisperLive` is the most complete wrapper, and the one that exposes the partial-versus-final distinction as a first-class API. Its `StreamingTranscriptionClient` takes callbacks named `on_partial_transcript` and `on_committed_transcript`, with `send(chunk, pcm_format="int16")` for audio, and the README documents the audio contract as "mono, 16 kHz PCM" ([README](https://raw.githubusercontent.com/collabora/WhisperLive/main/README.md)). Its self-description is "A nearly-live implementation of OpenAI's Whisper"; it states no latency figure in the README, only linking a blog post about "ultra-low latency" for the WhisperFusion product built on it. MIT licensed, last commit 10 September 2026. It is a server plus client, which for a desktop application means either a localhost process or importing its internals.

`QuentinFuxa/WhisperLiveKit` is the most active project in this space — 11,093 stars, Apache-2.0, last commit 21 September 2026 — and it is notable for two reasons. First, it states the problem as plainly as any source does: "Whisper is designed for complete utterances, not real-time chunks. Processing small segments loses context, cuts off words mid-syllable, and produces poor transcription. WhisperLiveKit uses state-of-the-art simultaneous speech research for intelligent buffering and incremental processing." Second, it ships an Apple Silicon path and not only a CUDA one: its optional-dependency table lists "Apple Silicon MLX Whisper backend" (`uv sync --extra mlx-whisper`) and a "Voxtral (MLX backend, Apple Silicon)" extra. It also lists a genuinely causal encoder, Qwen3-ASR-causal, described as "Causal streaming audio encoder for Qwen3-ASR: each audio block is encoded exactly once, constant compute per audio second, append-only transcripts" — which is the architectural answer to the quadratic cost problem in section 2, from a 2026 project rather than a 2023 policy ([README](https://raw.githubusercontent.com/QuentinFuxa/WhisperLiveKit/main/README.md)).

The summary table, with maintenance status as of the research date and the latency figure as stated by the source:

## 2. What the sliding window costs

The cost has a simple shape and it is worse than it first appears. Each update runs one full forward pass of the model over the *entire* unconfirmed buffer, not over the newly arrived audio. If updates happen every `C` seconds and nothing is trimmed, update `i` covers `i·C` seconds of audio, so an utterance of length `L` costs roughly `L²/(2C)` seconds of model work: quadratic in the length of the utterance. Trimming the buffer at `T` seconds makes each pass cover at most `T`, giving roughly `L·T/C` — linear in `L` but still a multiple of `T/C` times the work of transcribing the utterance once.

Both parameters are real defaults rather than hypotheticals. `whisper_streaming` uses `--min-chunk-size` 1.0 s and `--buffer_trimming_sec` 15, i.e. `C = 1`, `T = 15`, so it does about fifteen times the arithmetic of a single pass by design. The project's own `src/talktome/hearing.py` uses `STEP = 0.8` seconds and `LONGEST = 16.0` seconds, but deliberately does *not* trim — its docstring explains that "The buffer is never cut back mid-utterance... so the utterance is capped at a length the buffer can hold whole." That is a defensible correctness choice, and it makes the cost quadratic over the 0.8–16 s range rather than linear.

For the single-pass cost, the primary sources give figures for a GPU and for a larger model than ours. `faster-whisper`'s README benchmarks the `small` model on an Intel Core i7-12700K with 8 threads: 13 minutes of audio takes 2 m 37 s in fp32 and 1 m 42 s in int8, which is a real-time factor of roughly 0.20 and 0.13 respectively. The same table shows 1 m 6 s and 51 s with `batch_size=8` ([faster-whisper README](https://raw.githubusercontent.com/SYSTRAN/faster-whisper/master/README.md)). `base.en` is not in that table, and the table's hardware is not Apple Silicon, so it does not answer the question for this project.

I measured it instead, on the M1 Pro described at the top, using the `base.en` model TalkToMe downloads and its exact production settings. A single pass over a full utterance is fast — roughly twenty times faster than real time and close to linear in length:

| Utterance length | Wall clock | Real-time factor | Speed |
| --- | --- | --- | --- |
| 2 s | 0.279 s | 0.139 | 7.2× real time |
| 5 s | 0.414 s | 0.083 | 12.1× real time |
| 11 s | 0.608 s | 0.055 | 18.1× real time |
| 22 s | 1.069 s | 0.049 | 20.6× real time |
| 30 s | 1.441 s | 0.048 | 20.8× real time |
| 60 s | 2.689 s | 0.045 | 22.3× real time |
| 85 s | 3.351 s | 0.039 | 25.4× real time |

That table is why "20× real time" is a misleading headline for a streaming design. The sliding window multiplies it. Re-running the model on the whole buffer every `C` seconds, as `whisper_streaming` and `hearing.py` both do, produces this measured effective real-time factor for the *pipeline* — that is, seconds of model compute per second of audio, where a value below 1.0 means it keeps up:

| Configuration | Effective RTF | Verdict |
| --- | --- | --- |
| `C = 1 s`, trim at 15 s (whisper_streaming defaults) | 0.86–1.06 over three content regions | marginal; falls behind on some speech |
| `C = 2 s`, trim at 15 s | 0.31–0.45 | comfortable, ~2–3× headroom |
| `hearing.py` as specified: `STEP = 0.8 s`, cap 16 s, no trim, greedy | 0.84–1.27 over three content regions | falls behind on some speech |
| `hearing.py` with `STEP` raised to 1.2 s | 0.59–0.78 | keeps up |

Two things need saying about those rows. The first is that the `hearing.py` configuration is *specified in this repository* and is the exact design a stream-in/text-out recogniser would need. At `STEP = 0.8` it does not reliably keep up on a `base.en` model with four threads; at `STEP = 1.2` it does, with roughly 30 per cent headroom and no other change. That is a concrete, cheap adjustment available by changing one constant.

The second is tail latency, which is more awkward than the averages suggest. Per-update cost is content-dependent by a factor of about five, because the model's own temperature-fallback path re-decodes a window several times when it detects repetition. Holding the buffer length fixed at 15 seconds and varying only which 15 seconds of speech it contains, I measured per-update costs of 0.58 s, 0.59 s, 0.61 s, 0.64 s, 0.95 s, 0.97 s, 0.99 s, 2.22 s and 2.78 s with five repetitions each. So a pipeline whose *mean* cost fits inside its budget will still occasionally stall for nearly three seconds in the middle of a sentence. That is a user-visible stutter rather than a graceful degradation, and it argues for a commit interval with genuine headroom rather than one that only just fits on average.

The "greedy is much cheaper" assumption inherited from the docstring in `hearing.py` — "Partials run greedily, which is several times cheaper than the beam search the batch path uses" — is also worth correcting, because it is one of the reasons the design was believed to be affordable. Measured on the same machine, greedy decoding costs 1.23× to 1.49× less than `beam_size=3`, not several times less: 0.228 s versus 0.280 s at a 2-second buffer, and 0.665 s versus 0.991 s at 16 seconds. Greedy is still the right choice for partials, since partial text does not need beam search's accuracy, but it buys about a third rather than a factor. The dominant cost of the sliding window is the *repetition*, not the beam width.

There is one more CPU-specific caveat from a primary source, and it is the one that should temper any plan to make this the main recognition path. Given that Whisper has real word-error-rate costs when it is starved of context — the paper's own long-form section is a list of heuristics "to avoid failure cases of long-form transcription" ([Whisper paper, section 4.5](https://ar5iv.labs.arxiv.org/html/2212.04356)) — running it repeatedly on truncated buffers trades accuracy for latency in a way that is not measurable without a word-error-rate evaluation on real speech. Nothing in this note measures that trade-off, and it should be measured before the streaming path handles the user's actual words.

## 3. Genuinely streaming recognisers that run locally

Everything in this section is *architecturally* streaming, meaning the encoder consumes audio in blocks and maintains state across them, so that a partial transcript exists before the utterance ends. That is a different property from the sliding-window policies above, and it is the property that removes the quadratic cost. For each entry: licence, model size, whether interim results are real, and any stated latency or real-time factor. Latency numbers claimed by a model's own authors are marked as vendor claims; the ones printed by a console during an actual run are marked as measurements.

**Apple's Speech framework (`SFSpeechRecognizer`)** is the option that requires no model download at all, and it does support interim results: `SFSpeechRecognitionRequest.shouldReportPartialResults` is documented as "A Boolean value that indicates whether you want intermediate results returned for each utterance", defaulting to `true`, and `SFSpeechAudioBufferRecognitionRequest` "continuously analyzes the audio you appended, stopping only when you call the `endAudio()` method" ([Apple documentation](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/shouldreportpartialresults)). On-device operation is real but conditional, and the condition is a runtime check rather than a build setting: `requiresOnDeviceRecognition` "only honors this setting if the `supportsOnDeviceRecognition` property is also `true`", and Apple warns that "on-device requests won't be as accurate" ([Apple documentation](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition), [supportsondevicerecognition](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsonddevicerecognition)). The documented constraint that matters most is a hard duration cap: "Plan for a one-minute limit on audio duration. Speech recognition places a relatively high burden on battery life and network usage. To minimize this burden, the framework stops speech recognition tasks that last longer than one minute." Apple publishes **no model size, no parameter count and no latency or real-time factor** for the framework, so there is nothing to quote; whether the one-minute cap also applies when recognition is forced on-device is **not stated in the source**. There are Python bindings, `pyobjc-framework-Speech`, MIT licensed, requiring macOS 10.15 or later, whose own description defers to Apple for documentation ([PyPI](https://pypi.org/project/pyobjc-framework-Speech/)). For TalkToMe this is the only option that is free of model downloads and licence review, and the one-minute cap is compatible with a spoken turn.

**Moonshine** (`moonshine-ai/moonshine`, formerly `usefulsensors/moonshine`) is the strongest match for a streaming-first local recogniser, and it is the only option here whose streaming design is stated as the product rather than an add-on. Its README says it is "an open source AI toolkit for developers building real-time voice agents", that "Everything runs on-device — fast, private, and with no account or API keys", and that it is "Optimized for live streaming, with low latency by doing work while the user is still talking" ([README](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/README.md)). The API genuinely emits partials: `on_text()` "is called whenever the in-progress line changes", with events `LineStarted`, `LineUpdated`, `LineTextChanged` and `LineCompleted`, analysed "at a default interval of every 500ms of input" ([transcription docs](https://moonshine-voice.readthedocs.io/en/latest/using/transcription/)). Sizes and licences are unusually clean: English Tiny Streaming 34M and Small Streaming 123M and Medium Streaming 245M are all MIT, and the LICENSE file says "Moonshine models are released under the MIT License by default, in every language and at every size. This includes all streaming speech-to-text models and all English-language models", with the only exceptions being "the legacy non-streaming models for languages other than English" ([LICENSE](https://raw.githubusercontent.com/moonshine-ai/moonshine/main/LICENSE)). The latency figures are vendor self-measurements and have moved between releases: the current comparison page gives MacBook Pro response latencies of 59 ms for Medium Streaming, 38 ms for Small Streaming and 18 ms for Tiny Streaming against 11,286 ms for Whisper Large v3, while the older `v0.0.73` README gave 107 ms, 73 ms and 34 ms for the same three models ([comparison](https://moonshine-voice.readthedocs.io/en/latest/moonshine-vs-whisper/), [v0.0.73 README](https://raw.githubusercontent.com/moonshine-ai/moonshine/v0.0.73/README.md)). The vendor also defines the metric precisely and admits its limits: the logged latency is "the average time between when the library determines the user has stopped talking and the delivery of the final transcript of that phrase", the published cells are "medians of three runs taken with the device given time to cool between them", and some columns were "last taken before the build-optimization fix described in the changelog, so they read pessimistically" ([benchmarks](https://moonshine-voice.readthedocs.io/en/latest/using/benchmarks/)). The peer-reviewable version of the compute claim is the paper, whose abstract says Moonshine Tiny shows "a 5x reduction in compute requirements for transcribing a 10-second speech segment" against Whisper tiny-en at no word-error-rate cost ([arXiv:2410.15608](https://arxiv.org/abs/2410.15608)). It runs on ONNX Runtime on the CPU, with macOS arm64 builds documented, and no Metal or MLX path.

**`sherpa-onnx`** is the most mature option by breadth: Apache-2.0 licensed, macOS arm64 supported, actively maintained (last commit 22 September 2026), and its README states plainly that "both streaming and non-streaming are supported" ([README](https://raw.githubusercontent.com/k2-fsa/sherpa-onnx/master/README.md)). Interim results are structural rather than bolted on — the online result's `text` field is "Recognized text accumulated so far" — and the canonical Python loop is a short, honest statement of what streaming means: feed 100 ms blocks, `recognizer.decode_stream(stream)`, then `result = recognizer.get_result(stream)` and print only when it changes ([microphone example](https://raw.githubusercontent.com/k2-fsa/sherpa-onnx/master/python-api-examples/speech-recognition-from-microphone.py)). Streaming model families include Zipformer, Paraformer and CTC transducers, with a "small models" page explicitly targeting sub-Raspberry-Pi-4 hardware and listing 14M and 20M parameter English models ([Zipformer models](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html), [small models](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/small-online-models.html)). It is also the only option here whose documentation prints real-time factors from an actual one-thread run: the console output shows `Real time factor (RTF) = 0.04` for a Bengali streaming Zipformer on 7 seconds of audio with one thread, and `RTF = 0.46` for a Chinese xlarge int8 streaming Zipformer on 5.6 seconds — the slowest figure in the whole survey, and a warning that model choice dominates everything else ([Zipformer models](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html)). One premise worth correcting: the task brief asked about `--chunk-size` and `--pad-length` options. Those are not streaming options in `sherpa-onnx`; the online recogniser configuration exposes `feat_config`, `model_config`, `decoding_method`, `max_active_paths`, `enable_endpoint`, hotwords and the three endpoint rules, and **no `chunk_size` or `pad_length` field** ([c-api.h](https://raw.githubusercontent.com/k2-fsa/sherpa-onnx/master/sherpa-onnx/c-api/c-api.h)). Chunking is baked into the exported model, which is why model filenames carry strings like `chunk-16-left-64`. The real levers are model choice, endpoint rules, decoding method and `num_threads`.

**Moonshine and `sherpa-onnx` are the two options that fit this project's constraints** — CPU-only, local, permissive licence, real interim results — and they are also the two whose Apple-Silicon performance figures are least independently verified. `sherpa-onnx`'s numbers come from maintainer console output on unspecified Mac hardware; Moonshine's come from its own README tables. Neither has a third-party benchmark on Apple Silicon that I could find.

**NVIDIA Parakeet via MLX** is the option with the best Apple-Silicon *acceleration* story and the weakest streaming evidence. NVIDIA's own models are not streaming models: `parakeet-tdt-0.6b-v2` is a 600M-parameter FastConformer-TDT model whose only speed figure is a batched throughput claim — "an RTFx of 3380 on the HF-Open-ASR leaderboard with a batch size of 128" — and `parakeet-tdt-0.6b-v3` handles streaming only through NeMo's chunked-inference script (`chunk_secs=2`, `left_context_secs=10.0`, `right_context_secs=2.0`), which the card documents without stating any resulting latency or real-time factor. Both are CC-BY-4.0 ([v2 card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2/raw/main/README.md), [v3 card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3/raw/main/README.md)). The model NVIDIA actually trained for streaming is a different, smaller one: `nvidia/stt_en_fastconformer_hybrid_large_streaming_multi`, "around 114M parameters", with documented latencies of "0ms, 80ms, 480s, 1040ms" (the "480s" is a typo for 480 ms) and the note that "average latency of the model for each case would be half of these numbers"; the card is internally inconsistent about the `att_context_size` values that select those latencies, quoting `[70,16]` and `[70,33]` in one place and `[70,6]` and `[70,13]` in another ([card](https://huggingface.co/nvidia/stt_en_fastconformer_hybrid_large_streaming_multi/raw/main/README.md)). On Apple Silicon the path is `senstella/parakeet-mlx`, Apache-2.0, last commit 29 August 2026, whose README documents a real streaming context — `with model.transcribe_stream(context_size=(256, 256)) as transcriber:`, then `transcriber.add_audio(chunk)`, `result = transcriber.result`, with `finalized_tokens` and `draft_tokens` for commit decisions. It publishes **no latency or real-time factor for streaming** ([README](https://raw.githubusercontent.com/senstella/parakeet-mlx/master/README.md)). So Parakeet-on-Mac gives you Metal acceleration and interim tokens, but you would be the first to measure whether it is fast enough.

**Vosk** is worth knowing about chiefly as a baseline: genuinely streaming, Apache-2.0, with the clearest partial-versus-final API of any option — `if rec.AcceptWaveform(data): print(rec.Result()) else: print(rec.PartialResult())` — and a well-documented model zoo including `vosk-model-small-en-us-0.15` at 40 MB (9.85 per cent word error rate on LibriSpeech test-clean) and `vosk-model-en-us-0.22` at 1.8 GB (5.69 per cent) ([example](https://raw.githubusercontent.com/alphacep/vosk-api/master/python/example/test_microphone.py), [models](https://alphacephei.com/vosk/models), [install](https://alphacephei.com/vosk/install)). Its README claims "zero-latency response with streaming API", which is a claim rather than a measurement, and it is CPU-only with no Metal or MLX path.

**Kyutai's delayed-streams models** are the strongest genuinely-streaming research option, and the only one with a *quantified delay* as part of the model definition rather than the runtime: `kyutai/stt-1b-en_fr` is "~1B parameters, a 0.5 second delay" and `kyutai/stt-2.6b-en` is "~2.6B parameters and a 2.5 second delay", with "Streaming inference: the models can process audio in chunks, which allows for real-time transcription" and CC-BY-4.0 weights. There is an MLX implementation, tested on an iPhone 16 Pro for the 1B model ([README](https://raw.githubusercontent.com/kyutai-labs/delayed-streams-modeling/main/README.md)). The published throughput figures — "a H100 can process 400 streams in real-time" — are for data-centre GPUs and say nothing about an M1 Pro.

For completeness, the things that are *not* streaming and should not be adopted on the promise that they are: `mlx-examples`/`mlx-whisper` documents only `mlx_whisper.transcribe(speech_file)["text"]` and has no streaming API; Distil-Whisper is a faster batch model built for "sequential long-form" and "chunked long-form" algorithms, with the word "streaming" appearing in its card only in reference to Hugging Face dataset streaming; `nvidia/canary-1b-v2` uses "dynamic chunking with 1-second overlap between chunks", which is chunked batch; `aiola-stt` is a client for a hosted service, not a local model; and `kyutai/moshi` is a full-duplex dialogue model whose text stream is its own speech, not the user's transcript, despite advertising "a practical overall latency as low as 200ms on an L4 GPU".

## 4. Kokoro streaming

The answer here is more favourable than the project's current comment suggests, and also less useful. The comment in `src/talktome/speech.py` reads "Only ElevenLabs can generate from partial text. Local engines need the complete string, so they keep the sentence path." The first sentence is false as written (ElevenLabs is not unique — see below) and the second is true but does not imply the conclusion, because a *complete string* can still be synthesised into chunks that arrive before every chunk is ready. Those are two different things: incremental text input, and incremental audio output. Kokoro supports the second and not the first.

`kokoro-onnx` version 0.6.1, the version this project pins (`kokoro-onnx>=0.4.9,<0.7` in `pyproject.toml`), exposes an async generator in `kokoro_onnx/__init__.py`:

```python
async def create_stream(
    self,
    text: str,
    voice: str | NDArray[np.float32],
    speed: float = 1.0,
    lang: str = "en-us",
    is_phonemes: bool = False,
    trim: bool = True,
    sentence_pause: float = 0.25,
    clause_pause: float = 0.1,
) -> AsyncGenerator[tuple[NDArray[np.float32], int], None]:
```

It yields `(samples, sample_rate)` tuples. The docstring says "Stream audio creation asynchronously in the background, yielding chunks as they are processed", and abandoning the generator "stops the stream; the batch already running in the worker thread finishes, no further batch is started." The work runs in a thread pool via `loop.run_in_executor`, and an `asyncio.Queue(maxsize=1)` bounds look-ahead to one synthesised batch plus the one in flight. The bundled example, `examples/with_stream.py`, plays each chunk through `sounddevice` as it arrives ([source](https://raw.githubusercontent.com/thewh1teagle/kokoro-onnx/main/kokoro_onnx/__init__.py), [example](https://raw.githubusercontent.com/thewh1teagle/kokoro-onnx/main/examples/with_stream.py)).

The chunk granularity is the finding that decides whether this is useful, and it is coarse. Chunks are phoneme batches, and the batch limit is `MAX_PHONEME_LENGTH = 510` — measured not in phonemes or words but in **characters of the phoneme string** ([`config.py`](https://raw.githubusercontent.com/thewh1teagle/kokoro-onnx/main/kokoro_onnx/config.py), [`chunker.py`](https://raw.githubusercontent.com/thewh1teagle/kokoro-onnx/main/kokoro_onnx/chunker.py)). `split_phonemes` prefers to cut at sentence marks, then clause marks, then word boundaries, and then balances the batches so that no batch is much shorter than its neighbours. I phonemised real reply text with the project's own model and counted: 236 characters of English produced a 159-character phoneme string and therefore **one** batch; 756 characters produced an 807-character phoneme string and therefore two batches. Since that 159-character batch synthesised 8.98 seconds of audio and the 807-character string synthesised 44.5 seconds, a batch is worth roughly 9 to 25 seconds of speech.

The practical consequence is that `create_stream` yields exactly one chunk for a normal reply. Measured with the project's own `kokoro-v1.0.int8.onnx` and `af_heart`:

| Reply | Whole-utterance `create()` | `create_stream()` chunks | First chunk | All chunks |
| --- | --- | --- | --- | --- |
| 1 sentence, 57 characters | 1.574 s | 1 | 1.561 s | 1.561 s |
| 1 long sentence, 166 characters | 4.720 s | 1 | 4.704 s | 4.704 s |
| 3 sentences, 236 characters | 5.147 s | 1 | 5.154 s | 5.154 s |
| 16 sentences, 756 characters | — | 2 | 12.37 s | 24.65 s |

For the three-sentence reply the streaming API saves nothing at all: the first chunk *is* the whole utterance. Only past roughly 510 phoneme characters — somewhere around 500 to 750 characters of English, or several paragraphs — does a second chunk appear, and even then the first chunk takes 12.4 seconds to arrive.

There is **no published first-chunk latency figure** anywhere in the `kokoro-onnx` documentation or the `hexgrad/kokoro` project; the README's only performance claim is "Fast performance near real-time on macOS M1" ([kokoro-onnx README](https://raw.githubusercontent.com/thewh1teagle/kokoro-onnx/main/README.md)). The real-time factor implied by that claim is confirmed by measurement: 0.558 to 0.641 across the replies above, i.e. about 1.6 to 1.8 times faster than real time, with the model around 300 MB or 80 MB quantised. Kokoro's only diagnostic is a debug line, `Created audio in length of X for N phonemes in Y (RTF: Z)`, emitted via the logging module from `_infer`.

The reference implementation in `hexgrad/kokoro` is a different story and has no `create_stream` at all. Its `KPipeline.__call__` is a synchronous generator, `def __call__(self, text, voice=None, speed=1, split_pattern=r'\n+', model=None) -> Generator['KPipeline.Result', None, None]`, which splits the input on newlines by default, then on sentence boundaries for non-English, and yields a `Result` carrying `graphemes`, `phonemes` and `audio`. That is chunked generation at line granularity, not an audio stream ([`pipeline.py`](https://raw.githubusercontent.com/hexgrad/kokoro/master/kokoro/pipeline.py)). The project is Apache-2.0 and effectively dormant, last committed 6 August 2025 ([GitHub API](https://api.github.com/repos/hexgrad/kokoro/commits?per_page=1)).

One further feature is worth naming because it addresses a quality problem rather than a latency one. `create(..., continuous=True)` — and `_create_continuous` internally — synthesises long text "as overlapping windows" so that prosody carries across joins instead of every batch starting and ending as its own utterance. The example file states it "costs around 1.4x the work and needs a model exported with a duration output" ([`with_continuous.py`](https://raw.githubusercontent.com/thewh1teagle/kokoro-onnx/main/examples/with_continuous.py), [`sliding.py`](https://raw.githubusercontent.com/thewh1teagle/kokoro-onnx/main/kokoro_onnx/sliding.py)). The window constants there are `KEEP = 300`, `CONTEXT = 60`, `LOOKAHEAD = 60`, `CROSSFADE = 0.025`, and `continuous=True` raises `ValueError` on a model without duration outputs.

## 5. Is the endpointing angle real?

The user's hypothesis is that interim transcripts let the system decide the user has finished from linguistic completeness rather than from silence. The evidence says the underlying idea is sound and well measured, but that interim transcripts are not the usual input to it, and that at least one careful study finds text makes it *worse*.

The strongest single result is LiveKit's turn detector, which is the closest thing to a production semantic endpointing system. The original 2024 version was a 135M-parameter transformer fine-tuned from SmolLM v2 that consumes the accumulated transcript and "predictions are used to dynamically shorten or extend the VAD silence timeout", with the reported comparison: "In comparison to using VAD alone, EOU with VAD: Reduces unintentional interruptions by 85%; Falsely indicates that the turn is not over 3% of the time" ([LiveKit blog](https://livekit.com/blog/using-a-transformer-to-improve-end-of-turn-detection)). That is a two-number vendor claim with no described test set, and the baseline it beats is VAD with a 500 ms `min_endpointing_delay`.

The current generation is a 0.5B model distilled from a 7B teacher, shipped as quantised ONNX, at "396 MB" with "Per Turn Latency ~50-160 ms", and the model card documents English accuracy as 99.3 per cent true-positive rate at 87.0 per cent true-negative rate, with per-language tables for thirteen more languages ([model card](https://huggingface.co/livekit/turn-detector/raw/main/README.md), [docs](https://docs.livekit.io/agents/logic/turns/turn-detector.md)). It is important to note that the licence is **not** open source: "you may use these LiveKit models freely but can only use them together with the LiveKit Agents framework. You cannot use the LiveKit models on a standalone basis or with any other frameworks" ([LICENSE](https://huggingface.co/livekit/turn-detector/raw/main/LICENSE)). That alone rules it out for TalkToMe, which is not built on LiveKit. Its successor is audio-only and sidesteps the transcript question entirely: "two models that listen to the user's speech directly instead of waiting on a transcript, fusing semantic and acoustic understanding into a single end-of-turn prediction", and "the model no longer needs prior turns of chat context the way text-only versions did" ([LiveKit blog](https://livekit.com/blog/solving-end-of-turn-detection)).

The clearest *measured* improvement over a silence-only baseline comes from a harness rather than a product claim. LiveKit published `eot-bench` with open data and a committed report, in which the silence-only baseline scores 55.6 per cent false cutoffs at a 300 ms latency budget and needs 1600 ms of mean latency to reach a 5 per cent cutoff rate, against 9.9 per cent and 543 ms for their own v1 detector ([eot-bench README](https://raw.githubusercontent.com/livekit/eot-bench/main/README.md), [dataset card](https://huggingface.co/datasets/livekit/eot-bench-data/raw/main/README.md)). The obvious caveat is that the benchmark was run by a vendor with a competing product. The academic equivalents point the same way but at smaller magnitude: one preprint reports "0.97 boundary recall at 0.39 s median latency with 0.3 false fires per speech-minute" and states that "matching its recall costs a timeout 3× the latency and ~5× the false fires" ([arXiv:2609.04225](https://arxiv.org/abs/2609.04225)), and another reports "a 25.9% absolute improvement in endpoint accuracy within 320 ms over the strongest baseline" ([arXiv:2606.18094](https://arxiv.org/abs/2606.18094)). Both are preprints, not peer-reviewed papers.

The counter-evidence deserves equal weight, because it argues against the text-based version of the idea specifically. A 2026 preprint comparing acoustic, prosodic and text inputs under identical training conditions found that "the acoustic prosodic combination achieves the best balance of accuracy and latency, achieving utterance F1 of 0.93 with 7.8% false alarms at 400ms median latency", and that "**Adding text increases premature detections without improving performance.** ... These findings suggest that turn-taking is primarily conveyed through intonation and silence patterns rather than semantic completeness" ([arXiv:2609.11066](https://arxiv.org/abs/2609.11066)). The foundational work agrees that silence alone is insufficient — VAP's authors write that threshold policies "are well known to be insufficient for modeling human-like turn-taking, since silences inside of a speaker turn are often longer than silences between turns. Thus, such policies will either result in interruptions or sluggish responses" ([arXiv:2205.09812](https://arxiv.org/abs/2205.09812)) — and TurnGPT showed a transformer predicting turn-shifts from incremental text beats a POS-tagger and an LSTM baseline, with balanced accuracy rising from 0.690 to 0.789 on the Spoken set ([arXiv:2010.10874](https://arxiv.org/abs/2010.10874)). But neither reports milliseconds saved against a silence timeout.

On the specific question of whether **interim** transcripts feed these models, the answer from source code is no, with one exception. LiveKit's text model is fed the final transcript only: in the current source `_audio_transcript` is appended only on `stt.SpeechEventType.FINAL_TRANSCRIPT`, the interim hypothesis is held separately in `_audio_interim_transcript`, and the end-of-turn input is built as `chat_ctx.add_message(role="user", content=self._audio_transcript)`; interim text is folded in only on the explicit manual-commit path ([`audio_recognition.py`](https://raw.githubusercontent.com/livekit/agents/main/livekit-agents/livekit/agents/voice/audio_recognition.py)). Pipecat's Smart Turn takes no transcript at all — it is "Audio native — The model works directly with PCM audio samples, rather than text transcriptions", with `_predict_endpoint(self, audio_array: np.ndarray)` in the source ([README](https://raw.githubusercontent.com/pipecat-ai/smart-turn/main/README.md), [`local_smart_turn_v3.py`](https://raw.githubusercontent.com/pipecat-ai/pipecat/main/src/pipecat/audio/turn/smart_turn/local_smart_turn_v3.py)). Vocode, as the counterexample that has no semantic layer, is pure silence and punctuation: its `EndpointingType` enum contains `endpointing_time_based` and `endpointing_punctuation_based`, its `TimeEndpointingConfig.time_cutoff_seconds` defaults to 0.4, and "punctuation-based" means no more than "a shorter silence timeout after a terminal punctuation character" — a grep for `semantic`, `eou` or `end-of-turn` across its Python source finds no model ([`models/transcriber.py`](https://raw.githubusercontent.com/vocodedev/vocode-core/main/vocode/streaming/models/transcriber.py), [Deepgram transcriber](https://raw.githubusercontent.com/vocodedev/vocode-core/main/vocode/streaming/transcriber/deepgram_transcriber.py)). The one place partial hypotheses genuinely feed a turn model is a research prototype: FastTurn "combines streaming CTC decoding with acoustic features, enabling early decisions from partial observations", feeding a CTC transcript prompt into Qwen3-0.6B ([arXiv:2604.01897](https://arxiv.org/abs/2604.01897)).

Pipecat's Smart Turn is the most useful reference point for cost, because it is small and permissively licensed: **BSD-2-Clause**, "approximately 8M parameters", built from Whisper Tiny's encoder plus a linear classifier, shipped as an 8 MB int8 ONNX file, with vendor-measured inference of "12.6 ms" on an AWS `c7a.2xlarge` CPU and "3.3 ms" on an L40S ([README](https://raw.githubusercontent.com/pipecat-ai/smart-turn/main/README.md), [model card](https://huggingface.co/pipecat-ai/smart-turn-v3/raw/main/README.md), [v3 blog](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)). Its vendor-reported English accuracy is 94.31 per cent on 2,846 samples. Note that it still runs behind a silence detector rather than replacing one: `SmartTurnParams.stop_secs` defaults to 3.0, and "if a turn is classified as incomplete but silence continues for longer than `stop_secs`, the turn is automatically marked as complete" ([docs](https://docs.pipecat.ai/api-reference/server/utilities/turn-detection/smart-turn-overview.md)).

Finally, the human-factors premise that motivates all of this is well supported but the popular "<300 ms" formulation has no single canonical source. Levinson and Torreira put "the gaps between turns" at "of the order of 200 ms" while noting that language production "latencies involved ... are much longer (over 600 ms)", which is why speakers must project the end of a turn in advance ([Frontiers in Psychology](https://www.frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2015.00731/full)). Stivers and colleagues, across ten languages, found differences in average turn gap "within a range of 250 ms from the cross-language mean" ([PNAS](https://www.pnas.org/doi/abs/10.1073/pnas.0903616106)). No primary source I found asserts a hard threshold at 300 ms.

## What this means for TalkToMe

The decisive fact is the one the question already contains: for this system the dominant latency is a language model thinking for 30 to 120 seconds. Against that, the whole streaming-ASR project is worth about a second. The measured budget in `src/talktome/hearing.py`'s own docstring is "0.55–1.1 s of silence plus 0.32–0.47 s of transcription" — so the endpointing and transcription it replaces cost between roughly 0.9 and 1.6 seconds. Streaming recognition can recover most of that, and can remove the fixed wait after every complete sentence, but even a perfect result is 1.3 per cent of a 120-second reply and 5 per cent of a 30-second one. No amount of cleverness in the audio path changes the fact that the user is waiting on a model that has not started talking yet. If the goal is a faster-feeling system, the leverage is in starting synthesis earlier and speaking a progress signal, not in the microphone.

That said, streaming recognition is not therefore worthless, and the *reason* to do it is not latency. The real gain is that a pause to think stops being indistinguishable from the end of a turn. The existing comment in `hearing.py` is exactly right about this: "A pause to think and the end of a sentence look identical to an RMS threshold, so the app either cuts people off mid-thought or waits a fixed beat after every complete one." The endpointing literature in section 5 confirms both halves of that — VAP's authors say threshold policies "will either result in interruptions or sluggish responses", and LiveKit's benchmark measures the gap as 55.6 per cent false cutoffs versus 9.9 per cent for a semantic detector. So the honest case for the work is not "the reply arrives sooner"; it is "the user is interrupted less often and does not have to wait a fixed beat after every sentence". That is a quality-of-interaction argument, and it should be evaluated with an interruption count, not with a latency stopwatch.

Given that, the cheapest useful thing to change is the parameter that is currently wrong. `hearing.py` is already the right architecture — LocalAgreement-2 over a re-run buffer, greedy partials, silence demoted to one signal among several — and it is specified but not wired into the application. But `STEP = 0.8` with a 16-second untrimmed buffer measured an effective real-time factor of 0.84 to 1.27 on this machine, meaning it falls behind on some speech and will then behave worse than the batch path it replaces, because a queue that grows is a transcript that arrives later, not earlier. Raising `STEP` to 1.2 s drops that to 0.59 to 0.78 and keeps up with about 30 per cent headroom, at a cost of 0.4 seconds of additional partial-text latency. Trimming the buffer at 15 seconds, as `whisper_streaming` does by default (measured 0.86–1.06 at `C = 1 s`, or 0.31–0.45 at `C = 2 s`), bounds the per-update cost outright but requires deciding which audio is safe to discard, which `hearing.py` currently refuses to do for a good reason. Either change is a one-line edit and either is better than shipping the 0.8-second configuration as written.

The two claims in the docstring that the measurements do not support should be corrected before they are relied on further. Greedy decoding is 1.23 to 1.49 times cheaper than `beam_size=3`, not "several times cheaper"; the cost of the streaming path comes from re-running the model, not from the beam width. And a 0.8-second commit interval is not affordable on `base.en` with four threads. Both matter because they are the reasons the design was judged cheap enough to be free, and it is not free.

Looking outside the project, if the endpointing problem is taken seriously as a component rather than as a property of the recogniser, `sherpa-onnx` and Moonshine are the two candidates that fit the constraints — CPU-only, local, permissive licence, real interim results, nothing to licence from a competitor. `sherpa-onnx` is Apache-2.0, actively maintained, ships 14M and 20M parameter English streaming models, and prints a 0.04 real-time factor on macOS one-thread runs; Moonshine is MIT across all its streaming models, has 34M to 245M parameter options, and is the only one designed streaming-first with a documented 500 ms analysis interval. Parakeet via MLX is the fastest on paper but has no published streaming latency, and its NVIDIA cards document a different, smaller model as the streaming one. Apple's `SFSpeechRecognizer` is the zero-download option with genuinely documented interim results, and its one-minute duration cap is compatible with a spoken turn, but Apple publishes no latency or model size and does not document whether the cap lifts for on-device recognition. Any of these would remove the quadratic re-run cost entirely and free the endpointing decision from the recogniser's commit policy. None of them would be worth doing for the latency alone.

A semantic turn detector is a separate, cheap, and better-evidenced improvement, and it does not need a streaming recogniser to work. Pipecat's Smart Turn v3 is 8 MB, BSD-2-Clause, roughly 12.6 ms on a CPU, and takes raw audio rather than a transcript, so it would drop into the current whole-buffer design without any of the streaming work. That ordering matters: if the goal is fewer interruptions, the turn detector is a small, permissively licensed addition that the evidence supports, while the streaming recogniser is a larger change whose main measured effect is to make the partial text available a fraction of a second earlier. Doing the second before the first buys latency nobody will notice.

For synthesis, Kokoro's streaming API is real but its chunk granularity makes it nearly useless at this project's reply lengths. `create_stream` yields whole phoneme batches of up to 510 phoneme characters, which is roughly 9 to 25 seconds of speech; a 236-character three-sentence reply produced exactly **one** chunk, so first-chunk latency equalled total synthesis time (5.15 s in both cases). Only past roughly 750 characters does a second chunk appear. Kokoro's real-time factor is also only 0.56 to 0.64, so a nine-second reply costs about five seconds to synthesise — which is a real serial cost on the critical path, worth more attention than the streaming API. The genuinely useful local-TTS change is not `create_stream` but starting synthesis at the first complete clause of a streaming reply instead of the whole reply, which is what the ElevenLabs path already does in `src/talktome/streaming.py`; the sentence-splitting logic is the reusable part, and it needs the Kokoro batch boundary to be honoured rather than assumed. If `create_stream` is adopted, the guard is length: it changes nothing below about 510 phoneme characters and should not be presented as a latency fix until the reply is long enough for a second chunk to exist.

The overall shape of the answer to "stream input audio in, stream output chunks out" is that the two halves have opposite value. Streaming *input* is worth doing for interaction quality rather than speed, and its cost is measurable and manageable if the commit interval is raised above 0.8 seconds. Streaming *output* is mostly a non-issue at these reply lengths, and the project's existing sentence-level path already gets most of the available benefit. In both cases the dominant term is the language model, and the most valuable measurement this project could make next is not the latency of any speech component but the time from the end of the user's turn to the first audible syllable of the reply, broken down by stage. That number, which does not appear in the research cited here for any component, is the one that would say where the seconds actually are.
